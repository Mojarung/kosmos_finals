# FloodValue: оперативный атлас паводка

Рабочее место дежурного аналитика инфраструктурного оператора. По снимку Sentinel‑1 сервис строит карту паводка без постоянной воды, оценивает ожидаемый ущерб десяти объектов и собирает заказ дополнительной съёмки под бюджет и срок. Руководитель видит сравнение стратегий A/B/C и получает один ZIP с картами, таблицами, причинами выбора каждой зоны, параметрами и происхождением данных.

Работа идёт по шагам решения: **наблюдение → приоритет объектов → закупка → проверка качества и экспорт**. На 3D-карте можно выбрать область в любом месте Земли между 85° ю. ш. и 85° с. ш. Сервис находит снимки Sentinel‑1 RTC с VV и VH, объединяет соседние кадры одного прохода, запускает замороженный ансамбль и привязывает решение к дате наблюдения. Одна рамка обрабатывается до 300 км² и до 20 км на сторону; сетка имеет примерно 10 м/пикс., поэтому большой регион режется на фрагменты с перекрытием. Если часть пикселей без сигнала, фактическое покрытие показано отдельно.

Репозиторий сдачи: [GitVerse](https://gitverse.ru/hackrus.experts/kosmo-moskva_misis_zhomarung_cr7mentality_21), ветка `master`, веса в Git LFS там же. Рабочая копия команды: [GitHub](https://github.com/Mojarung/kosmos_finals), ветка `main`. Перед сдачей нужно отдельно подтвердить, что GitVerse доступен жюри и указывает на тот же commit: одинаковое имя ветки этого не доказывает.

[Свежая сверка 20 критериев и план работ](docs/18-diagnostic-after-service-iteration.md) отделяет готовность от баллов жюри. [Путь оператора по пункту 19](docs/19-operator-flow.md) описывает импорт, SkyFi и черновик заявки. [Карта документов](docs/README.md) ведёт к постановке и подробному разбору, [план пилота](docs/11-pilot.md) описывает проверку на реальном операторе.

## Запуск

Нужны Podman Compose или Docker Compose, а для нового региона доступ к Microsoft Planetary Computer. Три подготовленные сцены лежат в репозитории и работают офлайн. Ещё 446 официальных чипов Sen1Floods11 открываются из списка стран в шапке («Ещё N»): сервис скачает S1, ручную метку и слой постоянной воды JRC, запустит ту же замороженную модель и добавит сцену на карту. Расчёт идёт в контейнере на CPU весами из Git LFS, обучение и GPU не нужны. Повторное открытие берёт результат из томов `live-observations` и `runtime-observations`; импортированные проекты живут в `operator-projects`.

Сборка для сдачи требует чистого checkout: запуск через обёртку записывает точный Git commit в контейнер и каждый ZIP.

```bash
./scripts/compose.sh up --build
# Docker: CONTAINER_CLI=docker ./scripts/compose.sh up --build
```

На Windows/PowerShell: `$env:FLOODVALUE_COMMIT = git rev-parse HEAD; docker compose up --build`. При прямом вызове Compose передайте точный HEAD: без него сборка останавливается, чтобы экспорт не выдавал комплект с неизвестной версией. `FLOODVALUE_GITVERSE_COMMIT` задаётся отдельно после проверки зеркала и никогда не выводится из локального GitHub HEAD.

Интерфейс: <http://localhost:18080>. API: <http://localhost:18000/docs>. Порты задаются переменными `WEB_PORT` и `API_PORT`. На macOS, если Podman VM не пробрасывает порты, в отдельном терминале можно запустить `python3 scripts/podman_tunnel.py`.

Локальная разработка:

```bash
uv sync --project backend --extra demo --extra test
uv run --project backend uvicorn app.main:app --app-dir backend --reload
cd frontend && npm ci && npm run dev
```

## Что считает сервис

| Шаг | Источник | Результат |
|---|---|---|
| Вода | VV/VH Sentinel‑1, 5 моделей U‑Net ResNet34, калибровка Platt | p, маска при p ≥ 0,41, разброс ансамбля |
| Постоянная вода | JRCWaterHand Sen1Floods11 (вода и в 1984, и в 2018 году); для рамки на карте JRC Global Surface Water (вода и в 1984, и в 2021 году) | паводок = вода минус постоянная; обязательный EL = p × V × q считается и на постоянной воде, им же ранжируются объекты и корзина C; ущерб только от паводка (0 на ней) идёт отдельной колонкой |
| Сравнение | порог VH < −23,6 dB; ручная метка только для проверки | IoU/F1/precision/recall обоих методов на одних пикселях, всей воды и только паводка |
| Сомнения карты | шанс ошибки из калиброванной p: 1 − p на воде, p на суше | сомнительная площадь: шанс ≥ 8%, верхний дециль энтропии на validation; на независимом test_core там ошибается 29,4% пикселей против 4,6% в среднем |
| Ущерб | p в пикселе объекта, учебные V и q из кейса | EL = p × V × q для каждого из 10 объектов |
| Зоны | квадрат 1,12 км вокруг объекта, до пяти сомнительных участков по карте сомнений, вся область | каталог зон от 1 км² с причиной выбора или отказа для каждой |
| Закупка | бюджет, срок, обязательный объект, цель «ущерб» или «сомнения» | точный перебор всех корзин, стратегии A/B/C, кривая «цена → доля закрытых сомнений» |
| Цена | формула ПП №840 в редакции от 27.08.2025 | сценарная ставка 788,64 ₽/км², скидка по площади всей корзины, разбор цены на экране |
| Проекты | CSV или GeoJSON с точками, V, q и источником стоимости | собственные активы оцениваются по снимку отдельно от обязательных 10; версии решения сохраняют бюджет, A/B/C и состав активов |

Модель и baseline взяты из [ML-пакета проекта](ml/README.md), веса лежат в Git LFS. На независимом `test_core` (55 чипов, 11,56 млн валидных пикселей) IoU растёт с **0,519** у порога до **0,697** у модели, без постоянной воды JRC с **0,348** до **0,538**. На отдельном событии Bolivia: **0,535 → 0,655**. Это качество карты, а не оценка предотвращённого ущерба. Для новых регионов раздел «Качество» показывает эти числа как внешнюю проверку модели, а локальные IoU/F1 оставляет пустыми, пока нет ручной метки.

Для произвольной рамки каталог [Microsoft Planetary Computer Sentinel‑1 RTC](https://planetarycomputer.microsoft.com/dataset/sentinel-1-rtc) отдаёт снимки и даты. Сервер читает VV и VH из Cloud Optimized GeoTIFF, объединяет соседние кадры одного прохода, переводит яркость RTC в шкалу Sen1Floods11 GRD и запускает те же пять моделей без дообучения. Перевод нужен, потому что вода в RTC того же пролёта светлее: VH около −23 дБ против −27,5 дБ в GRD. Без перевода модель почти не видит воду. Квантильный перевод по каждой поляризации подобран на 13 чипах train и проверен на 11 независимых чипах test_core в виде RTC: IoU модели **0,184** без перевода, **0,637** после, на исходном GRD тех же чипов **0,684** ([проверка](ml/artifacts/evaluation/rtc_transfer.json), [скрипт](scripts/fit_rtc_harmonization.py)). Постоянная вода рамки берётся из JRC Global Surface Water v1.4 по тому же правилу, что у Sen1Floods11: вода и в 1984, и в 2021 году. Снимок исторический или актуальный на указанную дату, это не прямой эфир.

Сумма EL описывает модельную экспозицию учебного портфеля. «Ущерб в зонах» означает риск объектов, для которых планируется дополнительное наблюдение, и **не равен предотвращённому ущербу**. Разница стоимости B и C показывает экономию бюджета на данных при заданном тарифе, а не доказанный экономический эффект. Поставка новой съёмки (оптика через 6 часов, радар через 4 часа) остаётся сценарным допущением. В новой рамке координаты 10 объектов и V/q сценарные и не являются реестром инфраструктуры.

## Сцены и работа в интерфейсе

Три офлайн-сцены [Sen1Floods11 v1.1](https://github.com/cloudtostreet/Sen1Floods11): Nigeria_812045 (21.09.2018), Ghana_313799 (18.09.2018), Mekong_333434 (05.08.2018). Каждый GeoTIFF прошёл замороженный inference без дообучения. Стартовая сцена Нигерия: 14,8 км² воды, из них 13,18 км² паводка и 1,62 км² русла Кадуны по JRC.

1. Слева панель «Где вода»: паводок, река и суша одной полосой, сомнительная площадь и сравнение с порогом VH. Здесь же переключаются слои (вода, вероятность, сомнения, порог VH, ручная метка) и включаются радар и зоны заказа. Маска рисуется живой водой в WebGL: гладкий берег, глубина, рябь и пена, при открытии сцены паводок разливается от русла. Постоянная вода темнее и спокойнее. Растры при этом не меняются. Анимация идёт не чаще 30 кадров в секунду, только пока снимок в кадре, и замирает при `prefers-reduced-motion` или на слабой машине.
2. «Выделить рамкой»: мышью или пальцем выбрать область от 1,25 км по каждой стороне до 300 км². Каталог предложит до шести проходов с VV и VH, первый обработается сразу. После карты воды сервис сам берёт постоянную воду рамки из архива JRC Global Surface Water (2 секунды) и пересчитывает паводок.
3. Вкладка «Объекты»: рейтинг ущерба, вероятность воды, шанс ошибки карты и разброс моделей в точке объекта, чувствительность EL и места в рейтинге к ±20% p, V и q. Объект можно сделать обязательным в заказе. Если у объекта нет сигнала радара, его стоимость × уязвимость показана как неоценённый риск.
4. Вкладка «Съёмка»: бюджет, срок и цель. Под каждой стратегией написано, что она значит, рядом две полосы охвата: ущерб и сомнения. Ниже продающая фраза из текущих чисел, график «сколько сомнений закрывает каждый рубль», список зон с причиной решения и раскрываемый расчёт цены по ПП №840. Наведение на зону в списке подсвечивает её на карте.
5. Вкладка «Качество»: IoU модели и порога, отдельно только паводок, калибровка, как сомнения находят ошибки. Там же крупные снимки, где модель хуже порога: Bolivia_242570 (новое событие, его можно посчитать и открыть одной кнопкой) и India_747992 (test_adjacent); разбор обоих в [отчёте ML](ml/REPORT.md).
6. Клик по карте показывает точку: вероятность воды, паводок это или постоянная вода, шанс ошибки карты, порог VH и ручную метку.
7. В списке стран в шапке можно найти любую страну Sen1Floods11 и запустить расчёт. Если готовой сцены нет, участок выбирается сам, начиная с чипов, которых модель не видела при обучении.
8. Вкладка «Проекты»: создайте проект для текущего снимка, импортируйте CSV с колонками `name,longitude,latitude,value_rub,vulnerability,value_source` или GeoJSON Point с теми же свойствами. `source_date` можно указать дополнительно. Затем сохраните версию решения: снимок, бюджет, A/B/C и импортированные активы останутся в истории. Импорт не меняет обязательные 10 точек кейса. Из проекта можно открыть подбор SkyFi по своим объектам, сравнить цену в USD и охват EL, сохранить черновик заявки и скачать ZIP. Заказ поставщику не отправляется.

ZIP содержит `flood_probability.tif`, `flood_mask.tif`, `flood_uncertainty.tif`, `baseline_mask.tif`, `permanent_water.tif`, `assets.csv`, `asset_loss.csv` (все 10 объектов, EL = p × V × q, признак `in_region`, признак постоянной воды и ущерб только от паводка), `candidate_orders.geojson`, `zone_decisions.csv`, `procurement_plan.csv`, `strategy_comparison.csv` (охват ущерба и сомнений), `sensitivity.csv`, `metrics.csv`, манифесты с датами и лицензиями и `run_metadata.json` с таблицей обоснования параметров.

Проверка выгруженного комплекта одной командой (нужен `uv sync --project backend --extra demo`):

```bash
curl -o floodvalue-Nigeria_812045.zip 'http://localhost:18080/api/export?scene_id=Nigeria_812045&budget=6500'
uv run --project backend --extra demo python scripts/validate_package.py floodvalue-Nigeria_812045.zip
```

Валидатор проверяет обязательные файлы, 10 уникальных типов объектов, статусы только ok/partial/no_data, EL = p × V × q у каждого оценённого объекта (в том числе на постоянной воде) и нулевой ущерб только от паводка на постоянной воде, p в пикселе объекта, ранги по EL с равенством по asset_id, чувствительность каждого объекта, Polygon без вырезов и площадью от 1 км², цену B/C и группу скидки, охват ущерба B и C по геометрии, бюджет и равенство маски правилу p ≥ 0,41.

## Воспроизведение данных

Компактные выходы модели лежат в `data/demo`. Исходные GeoTIFF и промежуточный inference в Git не входят. Для полного пересоздания скачайте `S1Hand`, `LabelHand` и `JRCWaterHand` трёх чипов из бакета `sen1floods11/v1.1` в `data/source`, затем:

```bash
git lfs install --local
git lfs pull
uv sync --project ml
uv sync --project backend --extra demo
for chip in Nigeria_812045 Ghana_313799 Mekong_333434; do
  uv run --project ml floodvalue infer --s1 "data/source/${chip}_S1Hand.tif" --out "data/inference/${chip}"
done
uv run --project backend --extra demo python scripts/prepare_demo.py
```

В PowerShell цикл выглядит так, остальные команды те же:

```powershell
foreach ($chip in 'Nigeria_812045', 'Ghana_313799', 'Mekong_333434') {
  uv run --project ml floodvalue infer --s1 "data/source/${chip}_S1Hand.tif" --out "data/inference/$chip"
}
```

**Повтор обучения.** Полный прогон из чистого клона GitVerse на RTX 5070 занял 38 минут и дал те же веса побайтно: sha256 пяти файлов совпали с `ml/artifacts/model/model_card.json`, метрики те же (test_core IoU 0,6966, Bolivia 0,6551). На другой модели GPU веса могут отличаться в пределах разброса между seed (около 0,01 IoU на validation).

**Допустимая численная погрешность.** Повторный inference на другой платформе даёт те же маски. На Windows 11 x86-64 (CPU) маски трёх демо-сцен совпали побайтно, максимальная разница p 4,2·10⁻⁷, разброса ансамбля 5,8·10⁻⁷, ни один пиксель не перешёл порог 0,41. На macOS чистый клон повторил SHA‑256 всех растров. Допуск для проверки на CPU: |Δp| ≤ 10⁻⁶ при совпадающих масках. Между GPU и CPU у самого порога могут переключаться отдельные пиксели: на Bolivia_242570 это 0,13% пикселей (IoU 0,051 в GPU-оценке, 0,055 на CPU).

`scripts/prepare_demo.py` сверяет размер, CRS и сетку растра, фиксирует SHA‑256 источника и выходов, строит слои для карты и независимый от ручной метки учебный портфель, вычитает постоянную воду JRC. Метрики `test_core` и Bolivia копируются из [отчёта ML](ml/REPORT.md). Чтобы добавить постоянную воду к уже собранным сценам без повторного inference, есть `scripts/add_permanent_water.py`.

ML-этапы запускаются из папки `ml`, остальные из корня репозитория. Что именно пишет каждая команда, описано в [ml/README.md](ml/README.md#полный-прогон).

| Независимая проверка | `uv run floodvalue evaluate`, `uv run floodvalue failure --chip Bolivia_242570 --reference bolivia` | калибровка и порог по validation, метрики test_core и Bolivia, разбор провала |

| Объекты, зоны, A/B/C | `uv run --project backend --extra demo python scripts/prepare_demo.py`, затем `GET /api/analysis?scene_id=<chip>` | 10 объектов, EL, каталог зон, план C |

| Экспорт и проверка | `GET /api/export?scene_id=<chip>&budget=6500`, затем `scripts/validate_package.py` | ZIP из 21 файла, включая карту зон поверх снимка `zones_overlay.png`, `"status": "ok"` |

Основной метод и сервис используют только VV и VH Sentinel‑1, это и есть режим без вспомогательных данных. Вариант S1+S2 из ML-пакета в сервис не входит. Версии зависимостей зафиксированы в `ml/uv.lock`, `backend/uv.lock` и `frontend/package-lock.json`:

| Часть | Точные версии | Откуда |
|---|---|---|
| backend | Python 3.13 (образ `ghcr.io/astral-sh/uv:python3.13-bookworm-slim`), fastapi 0.141.1, uvicorn 0.54.0, numpy 2.5.3, rasterio 1.5.1, pyproj 3.8.0, pillow 12.3.0; для живого inference в образ ставятся torch 2.14.0+cpu, torchvision 0.29.0+cpu, segmentation-models-pytorch 0.5.0 | `backend/Dockerfile`, `backend/uv.lock` |
| ml | Python 3.13, torch 2.14.0+cu132 и torchvision 0.29.0+cu132 (на macOS 2.14.0 и 0.29.0 с PyPI), segmentation-models-pytorch 0.5.0, rasterio 1.5.1, numpy 2.5.3, scipy 1.18.1, scikit-learn 1.9.1 | `ml/.python-version`, `ml/uv.lock` |
| frontend | Node 22 (образ `node:22-alpine`), vue 3.5.43, vite 8.3.1, maplibre-gl 6.11.2; раздача через `nginx:1.27-alpine` | `frontend/Dockerfile`, `frontend/package-lock.json` |

Каждый комплект называет версию кода в `run_metadata.json/code_commit`. В контейнере hash передаёт обёртка запуска; `gitverse_commit` остаётся пустым, пока зеркало отдельно не сверено. Это предотвращает ложное утверждение, что любой GitHub commit уже опубликован в GitVerse. Итоговую версию перед защитой нужно проверить из чистого клона и пометить тегом.

`e2e_official.py` проходит скачивание, inference, анализ, пиксель, смену бюджета и ZIP. Браузерный путь проверяется на `http://localhost:18080`: рамка, дата, объект, план, экспорт.

- `backend/app`: FastAPI, анализ области, постоянная вода, карта сомнений и зоны (`zoning.py`), перебор корзин (`planning.py`), экспорт.
- `frontend/src`: Vue и 3D MapLibre, WebGL-слой воды (`lib/waterLayer.js`). Компоновка вдохновлена [krasnoyarsk_kosmos](https://github.com/Mojarung/krasnoyarsk_kosmos), инспектор точки и наклонный обзор приёмами [final_kosmostarsa](https://github.com/Mojarung/final_kosmostarsa), с другой палитрой и сценариями кейса.
- `ml`: пакет модели, веса, протокол split и независимая оценка.
- `data/demo`: реальные выходы модели для трёх сцен и слой постоянной воды; `data/catalog`: официальный список чипов.
- `scripts`: сборка демо-данных, валидатор, проверки переноса и постоянной воды, локальный туннель Podman.
- `docs/source`: постановка и критерии; `docs`: подробный разбор и [продуктовый сценарий](docs/product.md).

Kafka, Redis и внешняя LLM не нужны: новый снимок кэшируется по STAC ID и рамке, а таблица всех корзин строится один раз на область, поэтому смена бюджета, тарифа или цели пересчитывается за десятки миллисекунд без повторного inference.

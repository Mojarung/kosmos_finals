# Текущий код и требования кейса

Состояние на коммит `4227dbe` (25.09.2026).

В репозитории сейчас лежит сервис «Паводок: оперативный атлас»: FastAPI в `backend/app`, Vue 3 + Vite + MapLibre GL в `frontend/src`, SQLite, запуск через `compose.yaml`. Он берет готовые карты воды Copernicus GFM, контуры зданий OSM и каталог Sentinel из Planetary Computer STAC для любой территории, которую выберет аналитик.

Кейс устроен иначе: жюри оценивает собственную модель на Sen1Floods11, фиксированный портфель из 10 точек и цену по ПП 840. Большая часть текущей логики к критериям не относится. Ниже по пунктам.

| Требование кейса | Что есть сейчас | Вывод |
|---|---|---|
| Данные только из официального Sen1Floods11 (критерий 1) | GFM, OSM, STAC по произвольной территории | нужен отдельный пайплайн данных |
| Baseline и основной метод, метрики, split (2-8) | своих моделей нет, вода берется готовой из GFM | писать с нуля |
| Вероятности, калибровка, неопределенность (9, 10) | нет | писать с нуля |
| 10 точек, `EL = p·V·q` (13) | ущерб = площадь первого этажа × 80 000 ₽/м² (`backend/app/osm.py:25`) × доля по сценарной глубине 0,2-1,2 м (`backend/app/analysis.py:33`) | заменить моделью кейса |
| Цена по ПП 840 с пересчетом скидки (15, 17) | цена берется из предложений (`price_rub`), формулы ПП 840 нет | писать с нуля |
| Выбор плана под бюджет (15, 16) | точный перебор комбинаций с учетом перекрытий (`backend/app/planner.py`), вес объекта из стоимости, людей и критичности | идею перебора можно взять, целевую функцию и цену заменить |
| A/B/C (16) | нет | писать |
| Файлы сдачи (12) | экспорт GeoJSON, CSV зданий, JSON-отчет | форматы не совпадают, нужен свой экспорт |
| Интерфейс оператора с пересчетом бюджета (19) | карта, панели ситуации, последствий, съемки и данных | каркас подходит, содержимое менять |
| Репозиторий в GitVerse (11) | `origin` на GitHub: `github.com/Mojarung/kosmohakaton_2026` | добавить GitVerse remote, веса через LFS или релизы |

## Что стоит переиспользовать

- Каркас фронтенда: карта MapLibre, раскладка «карта + боковые панели», связь выбора в списке с подсветкой на карте. Для S1-чипа, растров p и маски, 10 точек и зон этого достаточно.
- Каркас FastAPI и `compose.yaml`: удобный способ дать жюри одну команду запуска.
- Из `planner.py` подход с точным перебором небольшого каталога и учетом уникального покрытия. Цену при этом надо считать по корзине целиком, иначе скидка ПП 840 посчитается неверно.
- Привычку сервиса подписывать допущения рядом с числами (раздел «Достоверность» в корневом README): жюри требует того же.

## Что мешает

- GFM, OSM, STAC и сетевые запросы в рантайме. Кейс требует воспроизводимого запуска на официальном чипе; внешние сервисы на защите только добавят точек отказа. Демо-событие «Учебный паводок · Валенсия» с синтетическими ценами к кейсу отношения не имеет.
- Модель ущерба через глубину и 80 000 ₽/м². Если оставить ее в основном интерфейсе рядом с EL, экономист в жюри увидит две несовместимые оценки ущерба.

## Предлагаемая раскладка

Я бы вынес ML и экономику в отдельный пакет на uv, который пишет комплект файлов из [06-deliverables.md](06-deliverables.md), а бэкенд и фронтенд сделал бы тонким слоем для просмотра комплекта и пересчета бюджета:

```
pipeline/            # uv-проект: данные, split, baseline, модель, EL, зоны, цена, A/B/C, экспорт
  data/              # загрузка Sen1Floods11, проверки набора
  models/            # baseline и основной метод
  economics/         # портфель, EL, чувствительность
  procurement/       # зоны, ПП 840, стратегии
  validate/          # проверка комплекта перед сдачей
outputs/<run_id>/    # комплект файлов одного запуска
backend/             # читает outputs, пересчитывает C при новом бюджете
frontend/            # показывает чип, p, маску, объекты, зоны, A/B/C
```

Пересчет бюджета в этой схеме трогает только `procurement` и не касается модели, что прямо требует критерий 19. Решение о раскладке за командой: если текущий сервис нужен для другой цели, его можно оставить в отдельной ветке.

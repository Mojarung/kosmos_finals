# Что сдавать

Источники: постановка, раздел III (с. 20-23), с. 19-20; критерии 11, 12, 19.

## Общие правила файлов

- Имена файлов и обязательные поля стандартизированы. Дополнительные поля и промежуточные файлы разрешены.
- Все файлы одного запуска (один S1-чип, один портфель, один бюджет) образуют согласованный комплект. После смены бюджета нужен новый комплект или явно обозначенная новая версия.
- CSV: UTF-8, разделитель запятая, десятичная точка. Отсутствующее измерение это пустое значение, а не `NaN`, `Inf` или 0.
- JSON и GeoJSON тоже без NaN и Inf.
- Все файлы получаются из кода, руками ничего не правим.

## Растры

| Файл | Формат | Содержимое |
|---|---|---|
| `flood_probability.tif` | GeoTIFF Float32, 1 канал | вероятность воды p от 0 до 1 по основному методу; nodata = -9999; CRS, transform, размеры и сетка как у S1-чипа |
| `flood_mask.tif` | GeoTIFF UInt8, 1 канал | 1 вода, 0 не вода, 255 nodata; для каждого валидного пикселя `mask = 1` ⇔ `p ≥ threshold` из `run_metadata.json` |

## Объекты и ущерб

**`assets.geojson`**: FeatureCollection ровно из 10 `Point` в WGS 84, порядок `[долгота, широта]`, по одному объекту каждого типа.

| Поле | Пример |
|---|---|
| `asset_id` | `A01` |
| `chip_id` | `Ghana_313799` |
| `asset_class` | `substation` |
| `asset_value_rub` | 20000000 |
| `vulnerability_coef` | 0.40 |

**`assets.csv`**: табличная копия тех же объектов: `asset_id, chip_id, asset_class, asset_value_rub, vulnerability_coef, longitude, latitude`. Значения и координаты совпадают с GeoJSON, связь с остальными файлами по `asset_id`.

**`asset_loss.csv`**: одна строка на каждый `asset_id`.

| Поле | Правило |
|---|---|
| `asset_id`, `chip_id` | как в `assets.csv` |
| `p_flood` | из `flood_probability.tif`, независимо от маски |
| `expected_loss_rub` | `p_flood × V × q` |
| `uncertainty` | выбранный показатель; смысл и статус в `run_metadata.json` |
| `rank` | 1 у максимального EL, при равенстве по `asset_id` |
| `status` | `ok` / `partial` / `no_data`; для двух последних неоцененные p, EL и rank пустые |

## Зоны и закупка

**`candidate_orders.geojson`**: каталог всех предложенных зон, валидные Polygon WGS 84 без holes, каждый от 1 км². Поля: `candidate_id, sensor_type, resolution_m, acquisition_type, data_role, observation_at, available_at, processing_level, usage_type, guaranteed_purchase, area_km2, base_rate_rub_km2, base_rate_status, base_rate_source`. Значения и смысл в [05-procurement-pricing.md](05-procurement-pricing.md#каталог-зон-candidate_ordersgeojson).

**`procurement_plan.csv`**: платные заказы B и C, для A строк нет.

```
strategy, candidate_id, area_km2, base_rate_rub_km2, base_rate_status,
processing_level, usage_type, guaranteed_purchase,
processing_coef, usage_coef, freshness_coef, discount_coef,
discount_group_id, group_area_km2, unit_price_rub_km2, cost_rub,
formula, legal_edition
```

Пара `(strategy, candidate_id)` уникальна; категориальные условия совпадают с каталогом и объясняют коэффициенты; `guaranteed_purchase` пишется как `true`/`false`. Скидка пересчитывается для каждой корзины целиком, итог стратегии равен сумме ее строк. Пустой план C допустим, если в бюджет ничего не влезает.

**`strategy_plans.json`**: точные составы, например `{"A": [], "B": ["Z01", "Z02"], "C": ["Z03"]}`. B и C используют только `candidate_id` из каталога, списки совпадают со строками `procurement_plan.csv`.

**`strategy_comparison.csv`**: одна строка на стратегию.

| Поле | Правило |
|---|---|
| `strategy` | A, B, C |
| `data_cost_rub` | сумма `cost_rub` из плана |
| `other_cost_rub` | прочие статьи, раскрытые отдельно |
| `decision_cost_rub` | `data_cost_rub + other_cost_rub` |
| `budget_rub` | ограничивает `data_cost_rub` |
| `budget_feasible` | C обязана быть `true`, B может быть `false` |
| `covered_expected_loss_rub` | уникально по `asset_id` |
| `coverage_share` | доля от оцененного EL портфеля; пусто при нулевом знаменателе |
| `residual_uncertainty` | пусто при `not_estimated` |
| `uncertainty_status` | `baseline` / `scenario` / `measured` / `not_estimated` |
| `uncertainty_basis` | формула или основание |

**`sensitivity.csv`**: одна строка на вариант параметров: `scenario_id, strategy, changed_inputs_json, decision_cost_rub, covered_expected_loss_rub, result_status, interpretation`. В `changed_inputs_json` что изменено (бюджет, V, q, ставка Б), в `interpretation` как и почему поменялся план.

Текущий экспорт делает по два отдельных варианта ±20% для p, V и q каждого из 10 объектов, пересчитывает корзину C, затем повторяет выбор для ±20% бюджета и сценарной ставки. Дополнительные столбцы `asset_expected_loss_rub`, `rank`, `zone_ids` делают изменение понятным без разбора вложенного JSON. Карта p и исходный портфель при этом фиксированы.

## Паспорт запуска и манифест

**`run_metadata.json`** собирает всё, что нужно для воспроизведения комплекта:

- `run_id`, исходные `chip_id` и `event_id`, S1-файлы, split;
- seed и правило размещения объектов;
- commit GitVerse, версии и веса обоих методов, их пороги и порядок проверки;
- модель EL и правило извлечения p;
- бюджет и `decision_deadline`;
- тариф, редакция ПП 840, правила скидки и группировки;
- как строились зоны и их доступность к сроку;
- единицы и способ расчета неопределенности;
- протокол и результат прокси-проверки ущерба: test-чип, правило контрольных точек, V/q, число точек, метрика ошибки;
- ссылки на файлы метрик и команды воспроизведения.

**`source_manifest.json`**: все исходные данные, включая обязательный S1 и дополнительные источники. Поля в [02-data-sen1floods11.md](02-data-sen1floods11.md#манифест-источников).

**Метрики двух методов**: имя файла не задано (см. вопрос 2 в [README](README.md#что-стоит-уточнить-у-организаторов)). Минимум: IoU, F1/Dice, Precision, Recall, число пикселей для baseline и основного метода на одном наборе, плюс разбивка по событиям.

Веса обученной модели лежат в самом GitVerse: Git LFS или релизы, с версиями и контрольными суммами. Сторонняя ссылка на веса требование не закрывает. Сам Sen1Floods11 и сторонние данные с ограничениями распространения в репозиторий не кладем.

Локальный комплект проверяется командой `backend/.venv/bin/python scripts/validate_package.py <zip>`. Наличие валидатора не заменяет публикацию в GitVerse и проверку запуска из чистого клона.

## Интерфейс оператора

Не файл, а рабочий инструмент. На экране:

- ID и дата выбранного S1-чипа, исходный S1;
- карта p и маска при зафиксированном пороге;
- 10 объектов с типами, EL и неопределенностью;
- кандидатные и выбранные зоны с ценой и сроками, причины отбора;
- A/B/C, бюджет, чувствительность;
- неизвестные участки и сценарные допущения рядом с числами;
- экспорт комплекта файлов.

Изменение бюджета пересчитывает C и итоговые показатели на том же портфеле и том же прогнозе, без переобучения и без смены порогов. Подойдет веб-приложение, карта с таблицей, GIS-проект или другой понятный вариант: жюри оценивает состав результатов, а не дизайн. В README команда запуска или URL развернутой версии.

## Сценарий защиты

Последовательность, которую показываем:

```
загрузка S1 из официального набора → p и бинарная маска → оценка 10 объектов
→ генерация и выбор зон → A/B/C
```

Жюри может на месте поменять бюджет, повторить inference на другом официальном S1-чипе и запустить обучение по README. К этому надо быть готовыми: команды должны работать с чистого клона.

Экономист в жюри будет различать ожидаемый ущерб, покрытый ущерб, затраты на данные и эффект решения. Если польза закупки только предполагается, в интерфейсе она подписана как сценарий.

# Фича «План выездов» — продуктовые требования и план реализации

Дата: 26.09.2026. Статус: **проект требований; реализация не начата**.

## 1. Задача оператора

«У меня есть список объектов и ограниченное число выездов. Какие объекты проверить первыми, сколько это будет стоить и что осталось непроверенным?»

Результат — сохраняемый план осмотра: выбранные объекты, очередь по приоритету, стоимость, объяснение выбора, статусы выполнения и результаты наблюдений.

План строится на существующих данных: текущая сцена, вероятности воды, координаты, стоимость и уязвимость объектов. Доступны учебные десять объектов и импортированный реестр проекта. Предположения о цене и ресурсах задаёт оператор. Назначение — поддержка решения оператора.

### Смысл денежных показателей

- Цена выездов — предполагаемые расходы на проверки.
- Ожидаемый ущерб объекта `p × V × q` — основание приоритета проверки имущества.
- Сумма ожидаемого ущерба выбранных объектов — охват проверками, а не предотвращённые потери.
- Выезд даёт наблюдение. Для расчёта предотвращённых потерь потребуются отдельная модель действий после осмотра и измерения их эффективности.
- Риск для людей и обязательность проверки критической инфраструктуры нельзя вывести из стоимости имущества. Оператор может закрепить обязательные объекты; это правило выше автоматического рейтинга.

## 2. Граница первой законченной версии

Включено: выбор объектов под число выездов и бюджет, обязательные/исключённые объекты, объяснения, карта, сохранение, выполнение, журнал наблюдений, история и экспорт. Один выезд означает одну проверку одного объекта.

План содержит **очередь по приоритету**, а не автомобильный маршрут. Количество доступных выездов оценивает оператор с учётом своих бригад и смены. Сервис не обещает время прибытия или проходимость дорог. Диспетчеризация сотрудников, транспортная сеть и автоматическая отправка заданий бригадам требуют отдельного этапа.

Для первой версии у всех объектов одна редактируемая цена проверки. Это соответствует текущему сценарию VOI и позволяет получить точный, понятный оптимум для реестров любого поддерживаемого размера. Разные цены, продолжительность и объединение нескольких объектов в одну поездку — отдельное расширение модели.

## 3. Пользовательский путь

1. Открыть «Объекты» → «План выездов» либо «План выездов» в выбранном проекте.
2. Указать, сколько проверок доступно, и цену одного выезда. Бюджет, обязательные объекты и исключения раскрываются по кнопке «Условия».
3. Получить выбранные объекты и цену. Нажать объект — увидеть его на карте. В «Почему выбран» раскрыть основание приоритета.
4. При необходимости закрепить конкретный объект. План пересчитывается; при конфликте условий показывается причина.
5. Нажать «Сохранить план». Сохраняются текущие входы, прогнозы и рекомендации.
6. В сохранённом плане отметить начало и результат осмотра. При недоступном объекте указать причину; замена формируется новым предложением и требует принятия оператором.
7. Скачать список заданий или открыть сохранённую версию позже.

Для исторической сцены видна пометка «Ретроспектива». Учебные планы и внесённые для демонстрации результаты обозначаются как учебные; они не становятся доказательством полевого пилота.

## 4. Функциональные требования

| ID | Требование | Приёмка |
|---|---|---|
| F01 | Явный источник объектов | В заголовке видны сцена/дата и «Учебные 10 объектов» или имя проекта; наборы не смешиваются |
| F02 | Максимальное число выездов K | Целое число от 0 до количества объектов; исходное предложение — min(3, N); результат не превышает K |
| F03 | Цена одного выезда | Неотрицательная сумма, одинаковая для всех объектов; предложенное значение 10 000 ₽ помечено как сценарное, доступно редактирование |
| F04 | Необязательный бюджет | Без лимита либо неотрицательная сумма; цена плана не превышает установленный бюджет |
| F05 | Обязательные объекты | Можно закрепить несколько объектов; обязательность выше рейтинга; превышение ресурсов даёт конфликт, а не тихое увеличение лимита |
| F06 | Исключения | Объект можно исключить с причиной. Совмещение «обязательный» и «исключённый» требует исправления |
| F07 | Выбор и порядок | Заполнять доступные места объектами с наибольшим ожидаемым ущербом; равенства разрешаются детерминированно |
| F08 | Объяснение каждого решения | Для включённого объекта — обязательность или место по приоритету; для остальных — лимит, бюджет, исключение, отсутствие данных либо уже выполненная проверка |
| F09 | Проблемные данные | Отсутствующая p, V или q не заменяется нулём. Такие объекты видны отдельно; их можно включить вручную как обязательные с пометкой «приоритет не рассчитан» |
| F10 | Карта | Выбранные объекты нумеруются; остальные приглушены. Клик по строке/маркеру выбирает один и тот же объект и сохраняет видимость карты |
| F11 | Цена и охват | На первом экране число проверок и стоимость. В подробностях — график приоритетов и оценённый риск выбранных/оставшихся объектов; неизвестный риск выделен отдельно |
| F12 | Сохранение | Снимок входных данных, версии модели, объектов, рекомендаций и источников сохраняется на сервере. Перезагрузка страницы сохраняет план |
| F13 | Выполнение | Статусы: «Запланирован», «В работе», «Проверен», «Недоступен», «Отменён». Статус проверки и наблюдение хранятся раздельно |
| F14 | Наблюдения | Результат: «Вода», «Сухо», «Не удалось определить»; время наблюдения, источник и комментарий. Сохранённые прогнозы модели остаются исходными |
| F15 | Перепланирование | Выполненные и начатые задания не назначаются второй раз. Их затраты/занятые выезды учитываются в остатке ресурсов |
| F16 | История | Изменение параметров или состава создаёт новую версию; сохраняется связь версий и журнал изменения статусов |
| F17 | Выгрузка | CSV заданий, GeoJSON точек и JSON расчёта/допущений в ZIP, плюс компактная печатная форма. Значения совпадают с сохранённой версией |
| F18 | Связь с текущим продуктом | Учебный A/B/C, закупка снимков и VOI продолжают работать. Цена проверки не складывается с ценой снимков без явного отдельного сценария |

### Параметры и валидация

- K — целое; цена и бюджет — конечные числа, без отрицательных значений, NaN/Infinity и пустых строк вместо чисел.
- Деньги рассчитываются в целых копейках; отображение и экспорт используют один порядок округления.
- Верхние технические границы полей фиксируются в API и UI: цена выезда до 10 млн ₽, бюджет до 1 млрд ₽.
- Обязательные и исключённые ID должны принадлежать выбранному набору объектов.
- Для p допускается [0, 1], для V — неотрицательное значение, для q — [0, 1]. Некорректная оценка не участвует в автоматическом ранжировании.
- При смене проекта/сцены старый ответ API не должен появиться как результат нового расчёта.
- Новые данные помечают открытый черновик устаревшим; сохранённая версия не пересчитывается задним числом.

## 5. Правило расчёта

Для оцениваемого объекта `R_i = p_i × V_i × q_i`. Задача — максимизировать сумму R выбранных объектов при одинаковой цене C, лимите K и необязательном бюджете B.

1. Убрать выполненные, занятые и явно исключённые объекты из нового назначения.
2. Проверить конфликты обязательных объектов и доступных ресурсов.
3. Вычислить число доступных мест: min(K, floor(B / C)) при C > 0 и заданном бюджете; иначе K.
4. Зарезервировать места обязательным объектам, включая неоценённые. Неоценённые не увеличивают денежную сумму охвата и отмечаются отдельно.
5. Остальные допустимые объекты с R > 0 отсортировать по убыванию R и заполнить оставшиеся места.
6. При одинаковом R выше ставить большую вероятность ошибки бинарного статуса, затем стабильный ID. Это правило очередности, а не гарантия калибровки неопределённости.
7. Вернуть список, порядок, цену, оценённые суммы выбранных/оставшихся объектов, неоценённые объекты и причины исключения.

При одинаковой цене выбор первых объектов по R даёт точный оптимум. Если в дальнейшем появятся разные цены поездок, правило сортировки придётся заменить оптимизацией под ограничения.

**Пустой результат:** K=0, бюджет меньше цены выезда или нет допустимых объектов. Причина показывается явно. При R=0 объект автоматически не выбирается; обязательность позволяет включить его вручную.

**Нет данных:** отсутствие оценки требует внимания, поэтому отдельная строка «N объектов без оценки» всегда видна и доступна для ручного решения. Она не спрятана среди низких приоритетов.

### Ресурсы при выполнении

Параметры сохранённого плана описывают всю смену. «В работе» и «Проверен» занимают слот и стоимость. «Недоступен» по умолчанию также занимает выезд: бригада могла уже потратить ресурс; оператор отдельно подтверждает, состоялся ли выезд. «Отменён» до начала освобождает резерв. Фактическая стоимость, если введена, хранится отдельно от сценарной.

Замена предлагается с учётом оставшихся ресурсов; исходное задание остаётся в журнале. После изменения лимита ниже уже использованных ресурсов отображается перерасход и новые назначения блокируются. Повторное нажатие «Сохранить»/«Проверен» не создаёт дубликат.

## 6. Интерфейс

### Размещение

- Основные разделы остаются: «Объекты», «Съёмка», «Проекты».
- В «Объектах» компактное переключение «Список / План выездов».
- В «Проектах» кнопка открывает тот же планировщик с реестром проекта и явным названием источника.
- Панель использует существующее раскрытие по ширине; на телефоне выбор точки временно освобождает карту.

### Первый экран

1. Заголовок «План выездов» и короткая строка источника/даты.
2. Поле «Доступно выездов» и «Цена выезда». Под ними компактная кнопка «Условия».
3. Итог: «3 проверки · 30 000 ₽» — пример для объяснения макета, не результат расчёта проекта.
4. Короткий список выбранных объектов с номером, названием, вероятностью воды и статусом. Обязательные отмечены значком и текстом.
5. Кнопки «Сохранить план» и, после сохранения, «Скачать задания».

По умолчанию не раскрыты: формулы, все невыбранные объекты, чувствительность, история и большой журнал. Причины выбора доступны по клику. Ошибки, конфликты, неизвестные оценки и ретроспективность остаются видимыми.

### Графики

- «Приоритеты проверки»: горизонтальные полосы R на одном масштабе, выбранные выделены; значения доступны текстом. График открывается в подробностях.
- «Выполнение»: после сохранения простой счётчик проверенных объектов и полоса прогресса по количеству заданий.
- Денежный охват не называется экономией. Деление на ноль и неизвестные значения не создают ложных процентов.

### Доступность и поведение

Клавиатура и видимый фокус, текстовые подписи статусов, цвет не является единственным отличием, графики имеют доступную таблицу. Нет горизонтальной прокрутки на 375/768/1440 px. Плавные короткие переходы, поддержка reduced motion. Поля и раскрытые блоки сохраняются при сворачивании. Несохранённые изменения обозначаются; при уходе с введённым результатом проверки предлагается сохранить или отказаться.

## 7. Технический план

### Уже есть — проверено по коду

- `backend/app/analysis.py`: текущая оценка сцены и объектов.
- `backend/app/projects.py`: импорт собственных объектов, SQLite и сохранённые снимки решений. `operator_plan` в нём относится к закупке снимков, поэтому сущности выездов получают отдельные имена.
- `backend/app/voi.py`: общий сценарий цены выезда 10 000 ₽ и экономические допущения; его формула не равна измеренной выгоде осмотра.
- `AssetsView`, `ProjectView`, карта, раскрываемая правая панель и экспорт.

### Новые компоненты

- Чистая функция планирования без сетевых запросов и inference; один и тот же расчёт для UI и экспорта.
- API: предварительный расчёт, сохранение плана, чтение версии, смена статуса задания/добавление наблюдения, создание новой версии, экспорт.
- Отдельные серверные сущности `field_visit_plans`, `field_visit_tasks`, `field_visit_events`; миграция без пересоздания текущих пользовательских таблиц.
- В плане: источник объектов, сцена/дата, хеш входов и версия модели, K/C/B, обязательные/исключённые ID, прогнозы на момент сохранения, версия/родительский план, режим учебный/операторский.
- В задании: ID объекта, координаты/название на момент сохранения, очередь, объяснение, прогноз, запланированная цена, текущий статус, затраченный ресурс.
- В событиях: время записи и наблюдения, старое/новое состояние, источник и комментарий; исправления добавляются в журнал.
- Блокировка устаревшей записи через revision; сервер сообщает конфликт при одновременных изменениях. Повтор запроса обрабатывается идемпотентно.
- `FieldVisitPanel` и небольшой адаптер состояния; карточки и карта используют стабильные ID объектов, включая проектные.
- Ответы API отменяются/отбрасываются при смене контекста; ошибки сохранения не выглядят как успешное сохранение.

Целевой отклик: изменение условий без повторного inference; после загрузки исходных оценок пересчёт для 10 объектов — до 1 секунды. Это цель приёмки, не измеренная сейчас характеристика. Для импортированного реестра отдельно измерить поддерживаемый объём и не скрывать долгую первичную оценку растра.

## 8. Этапы реализации и результат каждого

| Этап | Работа | Готовность этапа |
|---|---|---|
| 1 | Контракт данных и расчёт: одинаковая цена, K/B, обязательные, исключения, неполные оценки, объяснения | Unit-тесты и проверка оптимальности на малых перебираемых наборах |
| 2 | API, серверное сохранение, версии и безопасная миграция | Реальные запросы создают/читают план; перезапуск сохраняет данные; учебный и проектный наборы изолированы |
| 3 | Компактная панель, список/график, карта, обязательность и конфликты | Полный путь от текущей сцены и от проекта до сохранённого плана без подмены API |
| 4 | Выполнение, наблюдения, остаток ресурсов и замены | Статусы и наблюдения сохраняются, прогноз остаётся исходным, двойного назначения нет |
| 5 | CSV/GeoJSON/JSON и печатная форма | Выгрузка совпадает с сохранённой версией после смены сцены, переимпорта и обновления модели |
| 6 | E2E, визуальная проверка, короткая проверка понятности и подготовка демо | Все критерии ниже закрыты; ограничения и фактические результаты проверки записаны |

Каждый этап — отдельный проверяемый коммит на ветке `codex/…`. Процент готовности назначается по выполненным требованиям и проверкам, не заранее.

## 9. Проверки и критерий полной готовности

### Unit / API

- Выбранный набор оптимален при одинаковой цене; для малых случайных наборов совпадает с полным перебором.
- При увеличении K на неизменных данных выбранная сумма R не уменьшается; при равенствах результат стабилен.
- Бюджет/количество не превышены; цена 0, K=0, бюджет 0, дробные копейки обрабатываются корректно.
- Обязательные объекты, конфликт с исключением, нехватка ресурсов, неопределённые p/V/q и нулевой R.
- Собственный реестр не изменяет учебные десять объектов; повторный импорт не меняет сохранённый план.
- Начатые/выполненные/недоступные задания корректно расходуют ресурсы; замена не создаёт второй выезд на тот же объект.
- Идемпотентность, конфликт версий, устойчивость к перезапуску сервера, экспорт исходных входов.
- Наблюдение не меняет задним числом исходную p, EL и результаты backtest/VOI.

### E2E на настоящем backend

1. Учебная сцена → 3 выезда → сохранить → перезагрузить → тот же план → скачать задания.
2. 3 → 5 выездов: список/цена/график/маркеры согласованы, inference не запускается заново.
3. Обязательный объект ниже рейтинга попадает в план; невозможное сочетание условий даёт понятную ошибку.
4. Недостаточный бюджет / нет объектов / объект без p: корректные пустые и неполные состояния.
5. Объект → карта → начало проверки → результат → перезагрузка: журнал и прогресс сохранены.
6. Недоступность объекта → предложение замены → подтверждение: соблюдён остаток ресурсов.
7. Импорт проекта → план → новый импорт: старая версия и её экспорт неизменны.
8. Смена сцены во время загрузки, ошибка API, конфликт версий, повторное нажатие сохранить.
9. Клавиатура, 375/768/1440 px, reduced motion, быстрое сворачивание/раскрытие.
10. Регрессия существующих A/B/C, VOI, backtest, SkyFi, проектов и выгрузки.

### Понятность

Дать человеку, не знакомому с интерфейсом, без устных подсказок выполнить: выбрать три объекта, объяснить выбор, сделать школу обязательной, отметить результат и скачать задания. Целевой сценарий — до минуты до первого сохранённого плана. Проверить, что человек отличает цену проверки от ущерба и не принимает очередь за безопасный маршрут. Если внешнего участника нет, пометить проверку как эвристическую, не выдавать её за пользовательское исследование.

**Полностью готово:** F01–F18 работают на сохранённых серверных данных, проверки пройдены, интерфейс понятен в проверенном сценарии, выгрузка воспроизводима. Продуктовая готовность не означает подтверждение снижения реального ущерба.

## 10. Демо для защиты — около минуты

Открыть исторический пример с явной пометкой → задать 3 проверки → показать выбранные точки и цену → закрепить другой объект → показать замену и причину → сохранить → отметить учебный результат → скачать задания.
